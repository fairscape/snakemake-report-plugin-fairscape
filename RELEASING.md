# Releasing

Two different things propagate on two different schedules, so it helps to keep
them apart:

| Change | What has to happen | When it shows up |
| ------ | ------------------ | ---------------- |
| README, `docs/intro.md`, `docs/further.md`, any code | `git push` to `main` | the plugin catalog re-clones this repo every night (04:50 UTC) and re-renders the page, so docs land within a day without a release |
| anything a user should be able to `pip install` | a new version on PyPI | the same nightly job picks up the new version and re-reads its settings |

## Cutting a release

1. Bump the version in `snakemake_report_plugin_fairscape/__init__.py`:

   ```python
   __version__ = "0.1.1"
   ```

   That is the single source — `pyproject.toml` reads it via
   `[tool.setuptools.dynamic]`. Do not add a second version string.

2. Add the entry to `CHANGELOG.md`.

3. Commit, tag, push:

   ```bash
   git commit -am "release 0.1.1"
   git tag -a v0.1.1 -m "0.1.1"
   git push && git push --tags
   ```

4. Build and upload (needs `pip install build twine` and a PyPI API token in
   `~/.pypirc` or `TWINE_PASSWORD`):

   ```bash
   rm -rf dist
   python -m build
   twine check dist/*
   twine upload dist/*
   ```

   A version number can never be reused on PyPI, so if an upload is wrong the
   fix is always another version, never a re-upload.

5. Verify the way the catalog will:

   ```bash
   python -m venv /tmp/verify && /tmp/verify/bin/pip install \
       snakemake 'snakemake-report-plugin-fairscape[artifacts]'
   /tmp/verify/bin/python -c "
   from snakemake_interface_report_plugins.registry import ReportPluginRegistry
   print(len(ReportPluginRegistry().get_plugin('fairscape').get_settings_info()), 'settings')"
   ```

   This is exactly what the catalog does in its own throwaway environment
   (`pixi add snakemake-report-plugin-fairscape==<version>`, then
   `ReportPluginRegistry().get_plugin('fairscape').get_settings_info()`), minus
   the extras. If it works here it works there.

## When the conversion changes too

The Snakefile-to-EVI mapping lives in
[fairscape_conversion](https://github.com/fairscape/fairscape_conversion)
(`plugins/snakemake`). If a change spans both repos:

1. release `fairscape-conversion` first,
2. raise the floor here (`fairscape-conversion >=0.1.1,<0.2` in
   `pyproject.toml`) so a stale converter cannot silently produce an older
   crate shape,
3. then release this package.

The upper bound `<0.2` is deliberate: the records document that crosses the
boundary is a private contract between the two packages, and a minor bump there
is allowed to change it.

importable `process_crate`, `process_linkml` and `infer_schema` added in

Once fairscape-cli 1.2.10 is on PyPI, raise the floor to
`fairscape-cli >=1.2.10` in `pyproject.toml`. CI then starts asserting the
derived artifacts again on its own — `tools/run-examples.sh` checks for
`process_crate` and only demands the artifacts when they are possible.

## If the catalog page goes wrong

The page is generated by
[snakemake/snakemake-plugin-catalog](https://github.com/snakemake/snakemake-plugin-catalog);
its `Deploy` workflow log names the failure per plugin. The three ways this
package can break it:

- **"Cannot be installed"** — a dependency is not resolvable from PyPI
  (this is what would have happened before `fairscape-conversion` was
  published).
- **"Not a valid plugin"** — the package installs but
  `ReportPluginRegistry().get_plugin('fairscape')` or `get_settings_info()`
  raises.
- **"No documentation found"** — `docs/intro.md` disappeared from the repo
  root, or the `Repository` URL in `[project.urls]` stopped resolving. That URL
  is what the catalog clones; keep it exactly as it is.
